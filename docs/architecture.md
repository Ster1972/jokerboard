# Architecture

## System overview

Joker4P is a browser-only game client backed by a small Node.js server. The server serves files and coordinates rooms with Socket.IO. Gameplay and WebRTC run primarily in the browser.

```text
Browser / index.html
  -> sessionStorage room and player data
  -> src/scenes/joker4p.html
  -> Phaser 4 scene src/scenes/game.js
       -> Socket.IO signaling and game events
       -> WebRTC media to peer browsers
       -> Arcade physics and DOM video controls

Node.js server.js
  -> Express static file server
  -> Socket.IO room and event handlers
  -> RoomGameStore in src/helpers/serverstate.js
  -> in-memory users, marble snapshots, and card state
```

## Runtime entry points

- `server.js` is the HTTP, Socket.IO, and game-state process.
- `index.html` collects a player name and alphanumeric room name, stores both in `sessionStorage`, and navigates to the game page.
- `src/scenes/joker4p.html` loads Phaser, Socket.IO, WebRTC adapter, Bootstrap, and the module entry.
- `src/scenes/index.js` creates a Phaser game at 1490x825 and adds the `game` scene.
- `src/scenes/game.js` contains the main scene lifecycle, board rendering, game interactions, socket listeners, WebRTC setup, and collision logic.

## Server responsibilities

`server.js` creates an Express app, wraps it with an HTTP server, attaches Socket.IO, and listens on `PORT` or port 5056. `express.static("/")` is rooted at the repository directory, so static routes expose files below the repository root, including `node_modules`, subject to normal file access rules.

`RoomGameStore` is process-local and holds:

- connected and disconnected users by socket ID
- room membership and player numbers
- session reconnect tokens
- one marble snapshot array per room
- one card state object per room

State is not persisted to a database or shared across Node.js processes. A server restart clears all state.

## Critical server flows

### Join and reconnect

1. The client emits `joinServer` with room name, player name, and optional session token.
2. The server validates names against `^[a-zA-Z0-9]+$`.
3. Existing `Socket.IO` room membership is used for the four-player capacity check.
4. A disconnected player can reconnect when room, player name, and session token match.
5. New users receive a cryptographically generated 32-byte session token.
6. The server assigns player numbers 1 through 4.

Disconnected users remain in the store for five minutes before removal. If the room becomes empty, marble and card state are removed after the timer cleanup runs.

### Cards

`createHands()` shuffles 108 identifiers and deals six cards to each player. Eighty-four identifiers remain in the deck. Playing a card replaces it in the player's hand by shifting one new card from the deck; when the draw deck is empty, played cards are shuffled and recycled.

Card ownership is checked by player number and card position in `server.js`, but the implementation does not contain the turn/action methods referenced by the current tests (`activePlayer`, `pendingCardPlayer`, `completeMarbleAction`, or replay action IDs).

### Marble state

Each room stores a 23-element snapshot array: room name, 20 marble positions, turn text, and reset flag. `marbleState` is accepted for validated changes of up to 20 named marbles and is broadcast as `marbleStateDelta` with a monotonically increasing room sequence. Drag events also use `objMoveData` for lower-level movement broadcasts and `volatile` delivery every 33 ms.

### WebRTC

Socket.IO relays WebRTC offers, answers, ICE candidates, and room signaling. The browser requests camera and microphone access, creates peer connections, adds local tracks, and consumes remote tracks. TURN credentials are generated by the server only if both TURN environment variables are configured.
TURN credentials are cached for 54 minutes behind a 55-minute credential lifetime. Peer recovery uses disconnected/failed timers, while page navigation stops local tracks and closes all peer connections.
Peer setup is serialized and deduplicated per remote socket in the browser scene. SDP messages and ICE candidates use bounded per-peer queues, stale peer callbacks are guarded by peer identity, and ICE `disconnected` states attempt `restartIce()` before full recreation. Remote media uses one browser `MediaStream` per peer, while the local camera/microphone stream remains shared across all peers.
The browser records periodic WebRTC connection statistics at `window.__jokerWebRtcMetrics`, including state, bytes, lost packets, and round-trip time where the browser exposes those fields.

## Client structure

`game.js` creates the board holes, four marble groups of five, cards, player-name DOM controls, modals, drop zone, and 1490x825 Phaser scene. Collision helpers are spread across:

- `boardholes.js`: board-hole objects and nearest-hole lookup
- `playerballs.js`: player marble creation and metadata
- `marbles.js`: additional board/marble behavior
- `cards.js`: card image rendering
- `zone.js`: card drop zone
- `modal.js`: in-game modal
- `changename.js`: player-name modal
- `videohelp.js`: media and local video helpers

## External runtime dependencies

- Express 5 serves HTTP.
- Socket.IO 4 provides rooms, signaling, and recovery configuration.
- Socket.IO connection-state recovery is enabled in the server constructor.
- Phaser 4.2.1 provides rendering, physics, DOM elements, drag/drop, and scene management.
- Bootstrap is loaded for landing and instruction pages and video buttons.
- WebRTC adapter and browser media APIs provide peer media.

## Technical debt

- There is no build step, bundler, or asset pipeline.
- The 1219-line scene mixes rendering, networking, collision rules, turns, modals, and WebRTC.
- State is split across the store, local variables, DOM storage, and individual socket listeners.
- Player names, room names, session state, and board state rely heavily on `sessionStorage`.
- The card and turn state is incomplete relative to the test contract.
- Board/collision behavior contains nested and duplicated branches, especially in marble interaction functions.
- The repository includes generated review documentation and no CI workflow.
